## Findings and hard stop

The exact campaign would be `2026-09-25-preprod-mvp-002`. An address supplied by a user, its public hash, an output sent to it, or a DUST fee does not prove control. We need an authorized consumed input and a cryptographic, replay-resistant relationship to the receipt—not merely both appearing somewhere in a mergeable transaction.

1. **Public owner evidence exists in the API.** Installed indexer `dist/index.d.ts:210–246` documents `RegularTransaction.contractActions` and inputs consumed by that transaction; `UnshieldedUtxo.owner` is declared at lines 302–321. The executable `TX_ID_QUERY` in `dist/index.mjs:204–245` actually requests spent-output owner, intentHash, token type and value. Therefore the public query surface is established beyond field-name inference. Whether the specific future Preprod indexer is correctly serving finalized history is not established by that client code alone.
2. **Construction is unresolved.** Tagged connector 4.0.0 `makeIntent` (retained `v4.0.0-src-api.ts.txt:130–151`) can request unshielded inputs. `DesiredInput` (249–276) specifies kind/type/value, not owner, UTXO ID, receipt action or campaign. Wallet selection of inputs is intentionally delegated. `makeTransfer` specifies outputs; receipt ownership is not input authorization. The local SDK facade `initSwap` routes unshielded desired inputs to its unshielded wallet, then separately balances DUST fees (`dist/index.js:574–605`). This is useful capability evidence, not proof that 1AM 6.3.11 implements an exact owner/receipt construction safely. Its extension implementation is not installed source available for this review.
3. **Fees/balancing provide no general guarantee.** Connector balancing adds inputs as necessary. A zero-token-effect receipt may need DUST without consuming an unshielded input from the claimed address. Lower-level facade use requires wallet secret arguments and is not a permissible browser bypass. No raw wallet-state route or capability-signature retry is proposed.
4. **Same-transaction membership is necessary but insufficient.** Ledger `Intent.signatureData` and `UnshieldedOffer` document input-authorizing signatures and intent actions (`ledger-v8.d.ts:2034–2089`). `Transaction.merge` permits composition (`2399–2419`), and transaction hashes can change under merging; watch identifiers instead. A verifier must establish the claimed owner’s authorization of the specific receipt intent/action, not associate a public signed transfer with an unrelated receipt after the fact. This review does not assert that such an attack necessarily succeeds against a particular construction; no construction and full signature scope have yet been established. Appending actions to a bound intent is expressly restricted. We must not bypass that restriction or assume wallet-created sealed swap intent signatures cover later actions.
5. **Substitution is not yet prevented.** Any party can compute a claimed-address hash. A proper verifier would reject an owner mismatch, verify the signed receipt linkage and prevent replay across campaign/receipt IDs. That complete path has not been established; no companion contract should be implemented on the assumption that an arbitrary public-address input authenticates itself.
6. **Exact client query located, finality policy incomplete.** `watchForTxData` (`index.mjs:965–993`) polls `transactions(offset: { identifier: txId })`, takes a regular transaction, deserializes raw bytes, and returns block position plus execution/segment status. Its interface promises `FinalizedTxData` (`midnight-js-types/dist/index.d.ts:988–996`). It does not independently wait N confirmations or query a finalized head. It relies on indexer semantics; execution success/partial success is not a finality proof. We found no version-matched service implementation in this inspected corpus establishing the future endpoint’s finalized-only ingestion guarantee. No numerical confirmation depth is justified or invented. The exact installed query is saved as `installed-tx-id-query.graphql`; it does not itself select contract actions, which need an additional supported selection or validated ledger deserialization. No query was sent.
7. **Independent verification is plausible, not complete.** The transaction query needs only a public identifier, and public owner/action evidence could support ordinary third-party review. But receipt encoding, signed action linkage, endpoint finality assurance and duplicate policy remain unresolved. A trusted indexer response is also not a trustless inclusion/finality proof. No verifier or VERIFIED output exists here.

## Decision

Hard-stop conditions apply: required-owner construction, cryptographic receipt linkage and independently reviewable finality policy remain incomplete. This is not a claim that Midnight cannot support the design. It is a refusal to treat useful isolated APIs as a complete proof of the proposed workflow. No fifth V2 circuit, companion circuit, artifact generation, live UI control, service, wallet, proof, transaction or network operation was introduced. Repeated signData retries are not the critical path.

A separate design review must establish a supported single-intent/action authorization construction, its exact 1AM connector/ledger version bridge (the tagged connector transaction comments reference ledger-v6 while installed ledger is v8), canonical owner decoding, successful receipt segment linkage, replay/duplicate invariants and version-matched indexer finality semantics. Do not solve these by modifying the frozen credential protocol or collecting private wallet material. Only after this gate passes can implementation/local validation be considered.
