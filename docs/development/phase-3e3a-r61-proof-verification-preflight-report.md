### HTTP retry and redirect adjudication

The actual Node dependency path is provider 4.1.1 → fetch-retry **6.0.0** → cross-fetch **4.1.0** node-ponyfill → its nested node-fetch **2.7.0**. The repository's other node-fetch version is not substituted in this analysis.

* Provider retryOptions uses `retries:3`, statuses `[500,503]`, and `2 ** attempt * 1000` delay. fetch-retry starts at attempt 0 and retries while attempt < retries: **one initial fetch plus up to three retries**, four fetch attempts total per provider HTTP operation.
* HTTP 500/503 trigger retries. Other final statuses return to the provider, which throws if !response.ok. The fetch-retry catch branch also retries rejected fetch promises when retryOn is an array: network failures, aborts and other fetch rejection errors are not excluded by the configured status list.
* Delays are 1,000, 2,000 and 4,000 ms. The same init object, Uint8Array payload and AbortSignal are passed again; absent mutation, retry bodies are byte-identical. The provider constructs the payload once per operation. A single timeout signal is created before retries, so it is not a fresh per-retry timeout; after abort, scheduled retries may simply reject again.
* node-fetch defaults to redirect `follow` with up to 20 redirects **per fetch attempt**. The provider sets neither redirect nor follow controls. POST 301/302 and 303 switch to GET and remove the body; 307/308 preserve method/body. Redirects can leave loopback; sensitive-header stripping does not protect a retained binary witness body. Therefore four fetch attempts is not a bound of four wire requests in the presence of redirects.
* fetch-retry itself accepts per-call retry overrides, but the installed public ProvingProviderConfig exposes only timeout and headers. The provider's internally assembled init does not forward retry or redirect overrides. There is **no supported provider configuration demonstrated here** to disable either.
* Direct `prove` and transaction `proveTx` reach the same low-level provider/retry implementation. A transaction may require both check and prove operations and more than one circuit, so the total request count cannot be equated to four for the whole harness. A retried prove POST could repeat expensive server work; no idempotency mechanism is established by the inspected implementation.

The earlier conditional-plan preference for a custom native-fetch replacement is superseded. No custom transport is selected or implemented. Later choices are (a) explicitly authorize one logical harness run using the pinned provider's bounded retry behavior, **after** resolving redirects/privacy and exact operation count, or (b) stop pending a supported retry-free transport. A custom transport remains only a possible future reviewed proposal: exact createProvingPayload/createCheckPayload usage, key-material failure policy, response decoding, headers/content type, redirect:error semantics, abort/error behavior and timeout compatibility must all be demonstrated before implementation. It cannot be treated as an innocuous retry switch.
